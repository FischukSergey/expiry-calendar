# Duekeep — календарь истечений

Черновик функционала для согласования. Код и `ARCHITECTURE.md` появятся после утверждения этого файла.

**Duekeep** — личный и семейный/командный учёт всего, у чего есть срок: домены, SSL, подписки SaaS, договоры, гарантии, страховки, лицензии, налоги, ТО автомобиля. Главный вопрос продукта: *что сгорит в ближайшие дни и сколько это стоит*.

---

## Стек (черновик)

| Слой | Решение | Комментарий |
|---|---|---|
| Backend | **Go** | зафиксировано |
| Frontend | React + TypeScript + Vite | нет жёсткого предпочтения; это предложение — простой docker-образ и удобные графики |
| БД | PostgreSQL | удобнее иерархии категорий, фильтров и журналов, чем SQLite |
| Реалтайм | SSE или WebSocket | уведомления «истекает / истекло» без перезагрузки |
| Запуск | Docker Compose | backend + frontend + БД, одна команда |

Фронтенд можно сменить до начала плана разработки.

## Пользователи и роли

Регистрация и вход по JWT.

| Роль | Права |
|---|---|
| **admin** | полный CRUD записей, категорий, бюджетов уведомлений; продление; импорт/экспорт; просмотр журнала |
| **viewer** | просмотр записей, календаря, дашборда; поиск и фильтры; экспорт CSV |

Демо-аккаунты в seed (пароли только для локального демо, в README):

- `admin@duekeep.local` — admin
- `viewer@duekeep.local` — viewer

Оба видят **общий** набор демо-данных (одна «семья / домашняя лаборатория»), без мультитенантности в первой версии.

## Основные сущности

### Запись (item)

Единица учёта со сроком действия.

| Поле | Описание |
|---|---|
| title | название |
| description | свободный текст |
| type | тип: `domain`, `ssl`, `subscription`, `contract`, `warranty`, `insurance`, `license`, `tax`, `vehicle`, `other` |
| vendor | поставщик / регистратор / страховая |
| category_id | ссылка на категорию |
| tags | несколько текстовых меток |
| cost_amount | стоимость (может быть 0) |
| currency | ISO-код, в демо — `RUB` и `USD` |
| billing_period | `one_time`, `monthly`, `yearly` |
| started_at | дата начала / покупки |
| expires_at | дата истечения |
| notify_before_days | персональный порог, по умолчанию `30` |
| url | ссылка на кабинет / админку |
| account_hint | подсказка (логин, номер договора) **без паролей** |
| status | см. ниже |
| created_at / updated_at | служебные |

**Статусы** (часть вычисляется, часть задаётся вручную):

| Статус | Смысл |
|---|---|
| `active` | срок ещё далеко (дальше порога) |
| `expiring` | до `expires_at` осталось ≤ `notify_before_days` |
| `expired` | срок уже прошёл |
| `cancelled` | отменено вручную, в дашборд «сгорит» не попадает |
| `archived` | скрыто из основного списка, доступно фильтром |

Правило: `cancelled` и `archived` не пересчитываются автоматически.

### Категория

Иерархия (например: `IT → Домены`, `Дом → Техника`, `Авто`).

- CRUD категорий
- перенос записи в другую категорию
- глубина в первой версии — до 3 уровней
- удаление категории с детьми запрещено, пока есть записи или подкатегории (или перенос на родителя — уточнить)

### История продлений (renewal)

Каждое продление фиксируется отдельно:

- дата операции
- кто продлил
- старый / новый `expires_at`
- старая / новая цена
- комментарий

Продление **не удаляет** старую запись, а сдвигает срок и пишет историю.

### Уведомление (in-app)

- создаётся, когда запись переходит в `expiring` или `expired`
- прочитано / не прочитано
- клик ведёт на карточку записи
- дублируется в реальном времени всем активным сессиям

### Журнал аудита

Фиксируются создание, изменение, удаление, продление записи и изменение категории:

- пользователь, время
- сущность и id
- значения до / после (краткий JSON)

Журнал доступен admin.

## Функциональные требования

Общие требования задания входят в этот список, а не живут отдельно.

### Must have (сдаём обязательно)

1. **CRUD записей** с валидацией на клиенте и сервере  
   обязательны title, type, expires_at; cost ≥ 0; `started_at` не позже `expires_at`, если обе даты заданы.
2. **CRUD категорий** с иерархией до 3 уровней.
3. **Список записей** с пагинацией, поиском и фильтрами:  
   текст (название, vendor, теги), type, status, category, vendor, интервал `expires_at`, интервал стоимости, billing_period, тег.
4. **Карточка записи**: поля, статус, обратный отсчёт, история продлений, ссылка, подсказка аккаунта.
5. **Продление**: новая дата, опционально новая цена, запись в историю и в аудит.
6. **Дашборд**
   - карточки: всего активных, истекает за 7 дней, истекает за 30 дней, уже истекло, сумма ближайших продлений (месяц / год);
   - столбчатый график истечений по месяцам на 6 месяцев вперёд;
   - круговая диаграмма расходов по типу или категории;
   - таблица «сгорит раньше всех» (топ-10).
7. **Календарь** на месяц: отметки дней с истечениями, клик по дню открывает список. Навигация prev/next month.
8. **Импорт CSV** с маппингом колонок на поля записи (как в учебном трекере финансов).
9. **Экспорт CSV** текущего отфильтрованного списка.
10. **Реалтайм-уведомления** (SSE или WebSocket): смена статуса на `expiring` / `expired`, плюс колокольчик с непрочитанными.
11. **Роли admin / viewer**, JWT, два seed-аккаунта.
12. **Журнал аудита** для admin.
13. **Адаптивная вёрстка** desktop + mobile (список, дашборд, календарь, форма).

### Should have (хотим в первой версии, можно урезать)

14. Массовая смена категории / статуса у выбранных записей (admin).
15. Быстрые пресеты порога уведомления: 7 / 14 / 30 дней на карточке.
16. Сортировка списка: по дате истечения, стоимости, названию, обновлению.

### Out of scope (не делаем сейчас)

- email / Telegram / push в ОС;
- хранение паролей и секретов;
- автоматическое продление у регистратора / оплата;
- мультитенантность и приглашения в команду;
- вложения PDF/фото;
- iCal / Google Calendar;
- распознавание писем и чеков;
- полноценный биллинг и мультивалютный пересчёт в одну валюту (в демо просто разные `currency` у записей).

## Seed-данные

Реалистичный домашний + IT-набор:

- 2 пользователя (admin, viewer);
- ≥ 10 категорий, минимум 2 уровня;
- **50+ записей** за разные даты, из них:
  - ≥ 5 уже истекли,
  - ≥ 8 истекают в ближайшие 30 дней,
  - остальные распределены на 3–12 месяцев вперёд;
- типы: домены, SSL, SaaS (GitHub, iCloud, Cursor, доменный регистратор), страховка, гарантия техники, полис ОСАГО, ТО, налоговый срок, лицензия ПО;
- ≥ 20 записей истории продлений (в т.ч. с изменением цены);
- ≥ 15 записей аудита;
- несколько непрочитанных уведомлений.

## Критерии «готово» для демо

Преподаватель после `docker compose up`:

1. входит как admin и как viewer;
2. видит дашборд с графиками и ненулевыми цифрами;
3. фильтрует список, открывает карточку, создаёт и правит запись;
4. продлевает запись и видит историю;
5. открывает календарь текущего месяца с отметками;
6. импортирует маленький CSV и экспортирует фильтр;
7. видит уведомление без перезагрузки (вторая вкладка или смена даты в seed/админке);
8. открывает Swagger;
9. CI зелёный.

## Открытые вопросы

Ответы нужны до плана разработки. Рядом — предлагаемый дефолт.

1. **Фронтенд.** Оставляем React + TypeScript + Vite?  
   *Дефолт: да.*
2. **Область данных.** Общий список на двоих (семья / lab) или у каждого пользователя свои записи?  
   *Дефолт: общий список, разные роли.*
3. **Удаление категории.** Запрещать, если есть дети/записи, или переносить на родителя?  
   *Дефолт: запрещать удаление непустой категории.*
4. **Реалтайм.** SSE проще, WebSocket привычнее проверяющему.  
   *Дефолт: SSE.*
5. **Стоимость на дашборде.** Суммировать только `RUB`, игнорировать `USD`, или показывать раздельно?  
   *Дефолт: раздельно по валютам, без конвертации.*
6. **Регистрация.** Нужна публичная регистрация или только seed-логин + создание пользователя admin-ом?  
   *Дефолт: логин + регистрация (как в учебных вариантах), новые пользователи получают роль viewer.*
7. **Should have.** Массовые операции оставляем в v1 или вычёркиваем?  
   *Дефолт: оставляем, если не раздует срок.*
8. **Название репозитория / продукта.** Duekeep ок или переименовать?

После ответов (или «берём дефолты») следующим шагом будет `ARCHITECTURE.md` и план разработки — без кода.
