# Sprint 10 — оплата вхождения (календарь)

Источник: разбор после Sprint 9. Вариант 3: разреженная таблица платежей, не полная серия дат в БД. Спринты 1–9 не переписываем. Сдача `v1.0.0` не трогаем. Код — только когда пользователь попросил реализовать спринт.

## 1) Цель

«Оплачено» относится к **конкретной дате платежа**, не ко всей записи. Отметку ставят в календаре на конкретный день **и** на ближайшее open-вхождение с карточки и из soonest на обзоре (с телефона не ходить в календарь ради одной подписки).

К концу спринта:

- есть таблица `item_payments`: факт оплаты вхождения `(item_id, date)`;
- календарь показывает вхождение с суммой и статусом **дня** (`open` / `paid`); оплаченный день **остаётся** на сетке;
- карточка и soonest: та же ручка — оплатить **ближайшее** open-вхождение;
- «сгорит» / график / soonest / тикер смотрят ближайшее **неоплаченное** вхождение;
- `items.status = paid` из Sprint 9 остаётся заморозкой **всей** записи (форма), не основным путём для monthly/yearly.

## 2) Входные условия

- Sprint 9 в коде: развёртка `monthly`/`yearly` в памяти от `expires_at`; `items.status=paid` прячет текущий якорь; форма «Статус вручную».
- Календарь: клик по дню → title + бейдж статуса **записи**, без суммы и без действия.
- `renew` и история `renewals` без изменений контракта (сдвиг якоря — по-прежнему продление, не «оплатить 15-е»).

## 3) Границы

### Входит

- миграция `item_payments` + `owner_id`, уникальность `(item_id, paid_on)`;
- backfill: у строк с `items.status = paid` — платёж на `expires_at` (снимок `cost_amount` / `currency`);
- ручки отметить / снять оплату вхождения; календарь отдаёт сумму и `occurrence_status`;
- дашборд и тикер: неоплаченные вхождения; календарь: все вхождения окна, оплаченные с бейджем;
- UI календаря: сайдбар дня — название, сумма, статус вхождения, «Оплачено» / снять (admin);
- UI карточки и soonest (обзор): admin — «Оплатить» ближайшее open (та же `POST …/payments`);
- OpenAPI, тесты, limitations.

### Не входит

- материализация всех будущих дат в БД (строка только если пользователь отметил оплату);
- эквайринг, чеки, смена `cost_amount` в момент оплаты;
- статус вхождения `cancelled` / `archived` (они по-прежнему на записи);
- автосдвиг `expires_at` при оплате (это `renew`);
- экран истории платежей, CSV платежей;
- кнопка оплаты в **списке** записей и на **форме** (форма — заморозка `items.status`, не вхождение);
- UI «добавить тип», per-user kinds, почта, Telegram, `org_id`, шаринг, CD.

## 4) Backlog

### A. Схема

- Таблица `item_payments`: `id`, `item_id` (FK CASCADE), `owner_id` (FK users), `paid_on DATE`, `amount INT`, `currency CHAR(3)`, `created_at`.
- UNIQUE `(item_id, paid_on)`. Индекс `(owner_id, paid_on)`.
- Строка = оплачено. Снять оплату = DELETE.
- Goose после `012_paid_notify.sql` (например `013_item_payments.sql`).
- Backfill из `items.status = paid` → одна строка на `expires_at`. Статус записи не затираем.

### B. Смысл статусов

| Что | Где | Смысл |
|---|---|---|
| `occurrence_status` | календарь, платёж | `open` или `paid` **этого дня** |
| `items.status` | запись | `active`/`expiring`/`expired` считает тикер; `cancelled`/`archived`/`paid` — вручную на всю строку |

- Календарная кнопка **не** ставит `items.status = paid`.
- Форма «Оплачено» — заморозка записи (тикер молчит по всей строке), как Sprint 9.
- `cancelled` / `archived` по-прежнему не в календаре.

### C. Развёртка и агрегаты

Вхождения по-прежнему считает `period.go` от якоря. Поверх — множество оплаченных дат записи.

- Календарь: все вхождения в месяце; если есть платёж на день — `occurrence_status=paid`, иначе `open`. День не прячем.
- `expirations_by_month`, `expiring_7`/`30`, `soonest`: только **open**.
- `upcoming_cost` — run-rate Sprint 4, без изменений.
- Дата не из ряда записи (не тот день месяца / не `expires_at` у one_time) → `422`.

### D. Тикер

- `cancelled` / `archived` — как сейчас, не в `ListOpen`.
- `items.status = paid` — по-прежнему не трогать и не уведомлять (заморозка).
- Иначе порог и `expiring`/`expired` считать от **ближайшего open-вхождения ≥ today** (для one_time в прошлом — сам `expires_at`, если на него нет платежа).
- `notify_before_days IS NULL` — без notification и без `expiring`, как Sprint 9.

### E. UI: календарь, карточка, soonest

- Календарь, сайдбар: название (ссылка на карточку), `formatMoney`, бейдж вхождения, для admin — «Оплачено» / «Снять оплату» **этого дня**.
- Точки на сетке: цвет по `occurrence_status` (оплачено — как бейдж `paid`).
- Карточка и таблица soonest на обзоре: admin — «Оплатить» ближайшее open (`POST` с датой `next_open_at` / `soonest.expires_at`). Снять оплату там не обязательно (есть календарь).
- Viewer — только просмотр. Форму записи не раздувать; «Статус вручную» не убираем.

### F. Тесты и спека

- Отметить / снять; повтор POST идемпотентен; чужой item → 404; дата не из ряда → 422; viewer → 403.
- Monthly: оплата сентября не закрывает октябрь; сентябрь виден как paid.
- Dashboard: оплаченный день не в «сгорит» / столбце как open.
- Тикер: после оплаты близкого вхождения нет перехода в `expiring` из‑за этой даты.
- Backfill `status=paid` даёт строку платежа.
- OpenAPI + [`api-sprint-10.md`](api-sprint-10.md).

## 5) Техрешения

- Разреженный журнал, не расписание. Виртуальные даты + overlay оплаченных.
- Слои: `handler → service → repository`; scope `owner_id` из `sub`.
- Мутации пишут audit (`pay` / `unpay`), снимок без url/account_hint.
- POST: `ON CONFLICT (item_id, paid_on) DO NOTHING`, ответ существующей или новой строки (`200` / `201`).
- `amount`/`currency` — копия с item в момент отметки, дальше не синхронизируем.
- SSE/push новые события не вводим (это не смена `items.status` на expiring/expired).

## 6) DoD

- календарь: в дне видны сумма и статус вхождения; admin отмечает и снимает оплату;
- карточка и soonest: admin оплачивает ближайшее open без захода в календарь;
- monthly: закрытый день с бейджем, следующий цикл `open`;
- KPI «сгорит» без оплаченного вхождения;
- форма «Оплачено» на всю запись по-прежнему глушит тикер;
- контракт [`api-sprint-10.md`](api-sprint-10.md), OpenAPI, [`known-limitations-sprint-10.md`](known-limitations-sprint-10.md);
- `task lint` и `task test`.

## 7) Демо

1. Ежемесячная запись, якорь в далёком месяце — в ближайшем месяце на сетке есть день и сумма.
2. «Оплачено» в сайдбаре: день остаётся, бейдж оплачено; соседний месяц той же записи — `open`.
3. Обзор: это вхождение не в «сгорит»; из soonest — «Оплатить» на другой записи, строка уходит из топа.
4. Карточка: «Оплатить» ближайшее; дата совпадает с open-вхождением.
5. «Снять оплату» в календаре — снова `open`.
6. Разовая запись: оплата в календаре на `expires_at`.
7. Viewer не видит кнопок; чужой id — 404.

## 8) Риски

- перепутать `items.status` и `occurrence_status` в UI и тикере;
- валидация даты (clamp 29–31) разъедется с `period.go`;
- backfill `paid` + старое правило «прятать якорь» даст двойной смысл, пока календарь не переведён на overlay;
- идемпотентный POST vs 409 — зафиксировать в спеке.
