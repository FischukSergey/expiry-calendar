# Sprint 11 — исправления по ревью

Источник: разбор после Sprint 10. Спринты 1–10 не переписываем. Модель оплаты вхождения (`item_payments` + виртуальный ряд) остаётся. Код — только когда пользователь попросил реализовать спринт.

## 1) Цель

Продукт снова отвечает на вопрос «что уже просрочено». Демо-каталог диплома удалён. Общий справочник типов правит только роль `administrator`, которой на проде сейчас нет. Повтор уже прокрученного refresh реально гасит семью токенов.

К концу спринта:

- неоплаченное вхождение в прошлом даёт записи статус `expired`, пока этот день не оплачен;
- дашборд, фильтр «истекло» и бейдж карточки совпадают с open-днём в календаре;
- `seed.Run`, флаг `SEED` и демо-учётки `admin@` / `viewer@` убраны; процесс при старте больше не пишет записи, платежи, аудит и уведомления;
- `POST/PATCH/DELETE /kinds` разрешены только роли `administrator`; регистрация и все текущие пользователи прода эту роль не получают;
- reuse refresh коммитит revoke семьи; тест падает, если транзакция откатилась;
- карточка показывает обратный отсчёт, форма не даёт `started_at` позже `expires_at`, в списке есть bulk;
- push не принимает внутренний адрес, 500 пишутся в лог, login имеет лимит, CSV не начинает ячейку с формулы.

## 2) Что подтверждено в коде

| Замечание | Факт |
|---|---|
| Recurring не становится `expired` | `nextUnpaidOccurrence` для monthly/yearly пропускает дату `< today` (`period.go`, ветки `d.Before(from)`). Статус считается от следующего будущего вхождения. Разовая запись в прошлом по-прежнему может быть `expired`. Календарь берёт другой путь (`occurrencesInRange`) и показывает open-день в видимом месяце. |
| Документы ролей | Пункт 6 в `FUNCTIONAL.md` уже говорит: после Sprint 7 регистрация создаёт admin. Устарели `ARCHITECTURE.md` §7 («регистрация создаёт только viewer») и демо-формулировка «viewer смотрит общий каталог». |
| Kinds на всех | `Register` ставит роль `admin`. Мутации `item_kinds` завязаны на эту роль. Справочник общий. `TestRegisterCreatesAdminCanWriteKinds` фиксирует дыру как норму. На `duekeep.ru` регистрация открыта, и каждый пользователь уже `admin`. Отдельной роли хранителя справочника нет. |
| Reuse refresh | `RevokeFamily` внутри `tx`, затем `return ErrUnauthorized`. `db.RunTx` делает rollback. `nopTx` в тестах ошибку не откатывает, поэтому `Test` на семью после reuse зелёный. |
| 29–31 | Баг в том же цикле: `from.AddDate(0, i, 0)` при дне 29–31 перескакивает месяц. `occurrencesInRange` уже шагает от 1-го числа. |
| Push | `validateSubscribe` пускает любой `http`/`https` с хостом. |
| 500 | `writeDomainError` в ветке internal не логирует `err`. |
| Seed | Диплом сдан. Демо-набор (учётки, 50+ записей, история, платежи) больше не нужен. На проде `SEED=false` уже сейчас; локально `SEED=true` всё ещё пишет каталог при старте. |
| Integration | `task test:integration` печатает заглушку и выходит с ошибкой. `deploy/test/docker-compose.test.yml` (Postgres, порт 55432) не подключён. `go test` ходит в memory-fake. |
| Чистое, не трогать | SQL с параметрами. Чужой id предмета — 404. `task lint` — цель сохранить 0 замечаний. |

Регистрацию обратно в `viewer` не переводим: viewer не может создавать свои записи. Новый пользователь остаётся `admin` своих данных. Справочник типов остаётся общим на инсталляцию. Отдельная роль `administrator` — единственная, кому его можно менять. Свой справочник на пользователя не делаем.

## 3) Границы

### Входит

- правило статуса от самого раннего неоплаченного вхождения, включая прошлое;
- починка шага месяца в том же обходе;
- commit revoke при reuse и тест, который откатывает fake-транзакцию;
- роль `administrator` на мутации общего `item_kinds`; текущие `admin` прода её не получают;
- удаление демо-seed (`seed.Run`, `SEED`, учётки и каталог); типы — строками миграции, шаблон категорий регистрации остаётся;
- отсчёт на карточке, клиентская проверка дат, UI bulk;
- SSRF на push, лог 500, лимит login, защита CSV;
- `task test:integration` на одном сценарии с Postgres;
- точечные тесты фронта на отсчёт и порядок дат.

### Не входит

- свой `item_kinds` на пользователя, `org_id`, шаринг, почта, Telegram, вложения;
- наращивание seed до 200 записей и третьего уровня категорий;
- перевод всех ~117 тестов на Postgres и цель «100% repository»;
- e2e фронта и распределённый rate limit (Redis не заводим);
- закрытие регистрации;
- смена модели Sprint 10: ряд по-прежнему в памяти, в БД только отмеченные оплаты;
- CD и правки Sprint 8.

## 4) Backlog

### A. Просрочка ряда

Якорь статуса, `next_open_at`, soonest и «оплатить ближайшее» — **самое раннее неоплаченное** вхождение ряда.

- Нижняя граница ряда: `started_at`, если задан, иначе якорь `expires_at`.
- Дата `< today` и не оплачена → `items.status = expired`.
- `today ≤ дата ≤ today + notify` → `expiring`. Иначе `active`.
- Оплата этого дня (`item_payments`) сдвигает якорь на следующее неоплаченное. Пока прошлое вхождение open, запись не «переезжает» на следующий период.
- `cancelled` / `archived` / заморозка `items.status = paid` — как Sprint 9–10, тикер их не пересчитывает.
- Разовое вхождение в прошлом без платежа по-прежнему `expired`.
- `expiring_7` / `expiring_30` считают только даты в окне от today. Прошлое в них не попадает. В soonest просроченные идут первыми: дата якоря раньше.
- Обход месяцев — курсор с 1-го числа и `clampDay`, как в `occurrencesInRange`. Не `AddDate` от дня 29–31.
- Горизонт вперёд оставить (24 месяца / 6 лет). Назад идти от нижней границы ряда до первого неоплаченного, без сканирования «от начала времён».

Тест месяца: today = 2026-01-31, день якоря 31 → февральское вхождение 2026-02-28, март не подменяет февраль.

Тест просрочки: monthly, неоплаченное вхождение вчера, следующее в будущем → статус `expired`, `next_open_at` = вчера. После платежа на вчера статус считается от будущего дня.

### B. Refresh reuse

В `Auth.Refresh`, если строка уже отозвана:

1. `RevokeFamily` в той же транзакции;
2. вернуть `nil` из колбэка, чтобы `RunTx` сделал commit;
3. снаружи вернуть `ErrUnauthorized` и не выдавать новую пару.

Неизвестный токен по-прежнему 401 без revoke.

Fake `TxFunc` для теста reuse: снимок хранилища refresh, при ошибке колбэка — откат. Старый код (revoke + return error) на этом fake обязан провалить тест «семья мертва». `nopTx` для остальных тестов можно оставить.

Integration, build tag `integration`:

- поднять `deploy/test/docker-compose.test.yml`;
- миграции на эту БД;
- сценарий: login → refresh → повтор старого refresh → новый refresh тоже 401;
- `task test:integration` поднимает compose, гоняет `go test -tags=integration`, гасит compose;
- обычный `task test` тег не включает.

В CI — отдельный job с service Postgres и тем же тегом. Юнит-job без Docker не трогать.

### C. Роль администратора справочника

Справочник `item_kinds` остаётся один на инсталляцию. Отдельная копия на пользователя не заводится.

Миграция расширяет `users.role`: к `admin` и `viewer` добавляется `administrator`. Существующие строки не повышаются: на проде все остаются `admin`.

| Роль | Свои записи, категории, оплаты, import, bulk | `POST/PATCH/DELETE /kinds` |
|---|---|---|
| `admin` | да | нет, 403 |
| `viewer` | нет, 403 | нет, 403 |
| `administrator` | да | да |

- `Register` по-прежнему создаёт `admin`. Роль `administrator` из регистрации не выдаётся.
- Проверка kinds — по claim `role` в access, как остальные мутации. Отдельный флаг в таблице не нужен.
- `GET /kinds` остаётся любому auth.
- Назначить администратора можно только с сервера: env `ADMINISTRATOR_EMAIL`. На старте и при register/login, если email совпал и пользователь уже есть, роль становится `administrator`. Пустой env — справочник только для чтения. Публичной ручки смены роли нет.
- Тест `TestRegisterCreatesAdminCanWriteKinds` заменить: регистрация создаёт свою запись и получает 403 на `POST /kinds`. Отдельный тест: пользователь с ролью `administrator` создаёт kind; `admin` и `viewer` — нет.
- UI смены роли и экран пользователей не делаем. Формы записи kinds и так нет: закрытие — на API.

Роль `viewer` в схеме остаётся. Демо-учётку `viewer@` удаляем вместе с seed. Новых viewer никто не создаёт.

Документы (вместе с кодом):

- `ARCHITECTURE.md` §7: регистрация создаёт `admin` своих данных; kinds пишет только `administrator`;
- `FUNCTIONAL.md`: убрать демо-аккаунты и норму seed-каталога; регистрацию в `viewer` не возвращать.

### D. Удаление seed

Дипломный набор больше не пишется и не проверяется. Норму «200+ / 6 месяцев / 3 уровня» в требования не переносим.

Уходит:

- `seed.Run` и вызов из `cmd/server`;
- env `SEED`, `SEED=true` в local compose, `SEED=false` в prod compose;
- демо-пользователи, их категории, записи, продления, аудит, уведомления, платежи;
- `CheckCatalog` с порогами «≥50 записей», «≥5 expired» и соседние тесты фикстур.

Остаётся, но это уже не seed:

- десять типов (`subscription`, `rent`, `mobile` и остальные) переносятся в goose-миграцию с `ON CONFLICT DO NOTHING`. `EnsureKinds` при старте удаляется. На уже засеянной прод-базе миграция ничего не дублирует;
- шаблон категорий для **нового** пользователя при `Register` остаётся продуктовым поведением. Код переезжает из пакета `internal/seed`, пакет после этого удаляется.

Уже записанные в локальный volume демо-строки миграция не стирает: на проде их нет (`SEED=false`), а удаление чужих items по имени опасно. Чистый локальный стенд — новый volume. В README убрать пароли `admin@` / `viewer@` и описание демо-каталога.

### E. UI

- Карточка: отсчёт до `next_open_at`. Прошлое — «просрочено на N дн.», сегодня — «сегодня», будущее — «через N дн.». Нет open-вхождения — блок не показывать. Считать от календарного дня UTC, как тикер.
- Форма: если заданы обе даты, `started_at` не позже `expires_at`. Сервер уже отвечает 422 (`invalid dates`). Клиент показывает ошибку поля до запроса.
- Список, роли `admin` и `administrator`: выбор строк и панель «категория и/или статус» → существующий `POST /items/bulk`. Новой ручки нет. `viewer` чекбоксы не видит.

### F. Сеть, лог, экспорт

- Push: только `https`. Хост резолвится; любой адрес из loopback, private, link-local, multicast, unspecified — 422 на subscribe. Та же проверка непосредственно перед отправкой: внутренний адрес не запрашивать, ошибку залогировать, остальные подписки не останавливать.
- 500: один helper пишет `slog.ErrorContext` с `err` и путём, клиенту по-прежнему `internal` без текста ошибки. Тела, пароли и токены в лог не класть. 4xx не логировать как error.
- Login: in-memory счётчик неудач на пару IP + email. 8 неудач за 15 минут → 429 до конца окна. Успешный login сбрасывает этот ключ. Refresh не лимитируем. Лимит на процесс, сбрасывается рестартом — это в limitations.
- CSV export: текстовая ячейка, которая начинается с `=`, `+`, `-`, `@`, таба или CR, получает префикс `'`.

### G. Тесты фронта

В проекте нет `npm test`. Поднять Vitest только на чистые функции: текст отсчёта и отказ формы при `started_at` > `expires_at`. Подключить скрипт `test`, чтобы `task test:frontend` и CI-job frontend его вызывали. Страницы e2e не пишем.

## 5) Техрешения

- Слои прежние: `handler → service → repository`. Scope `owner_id` из `sub`.
- `item_kinds` остаются общими. Пишет только роль `administrator`. Регистрация эту роль не выдаёт.
- Revoke при reuse коммитится. Откат оставляем для ошибок выдачи новой пары на живом токене.
- Integration отделён тегом, чтобы `go test ./...` не требовал Docker.
- Лимит login и SSRF-проверка — в процессе, без Redis и без нового сервиса.

## 6) DoD

- monthly с неоплаченным днём в прошлом: карточка и фильтр `expired`, календарь показывает тот же open-день; оплата дня снимает `expired`;
- today на 29–31 не пропускает короткий месяц;
- старт без `SEED`: в базе нет демо-учёток и демо-записей; десять типов на месте из миграции;
- новый пользователь создаёт item и получает 403 на kinds; `administrator` kinds меняет; существующий `admin` — нет;
- повтор старого refresh гасит новый (юнит с откатом fake и integration на Postgres);
- отсчёт, клиентская дата, bulk категории/статуса;
- push на `http://127.0.0.1` и частный IP → 422; 500 есть в логе; 9-й неудачный login → 429; ячейка `=1+1` в CSV с префиксом;
- контракт [`api-sprint-11.md`](api-sprint-11.md), OpenAPI, [`known-limitations-sprint-11.md`](known-limitations-sprint-11.md);
- `FUNCTIONAL.md` и `ARCHITECTURE.md` сходятся с правилами выше;
- `task lint`, `task test`, `task test:integration`.

## 7) Демо

1. Чистый старт: нет `admin@` / `viewer@` и нет демо-записей. В `GET /kinds` есть прежние типы, включая «Мобильная связь».
2. Зарегистрированный пользователь создаёт ежемесячную запись с якорем в прошлом месяце без платежа: дашборд `expired` > 0, фильтр находит её, в календаре тот день `open`, бейдж записи `expired`.
3. «Оплатить» этот день: статус уходит с `expired`, следующий период `open`.
4. Тот же пользователь: `POST /kinds` → 403. Пользователь с ролью `administrator` (email из env) создаёт kind.
5. Два refresh подряд, затем повтор первого: второй тоже 401.
6. Карточка показывает «через N дн.» или «просрочено на N дн.».
7. Форма с началом позже срока не уходит на сервер.
8. Две строки в списке: bulk меняет категорию.
9. Экспорт строки с названием `=1+1` — ячейка начинается с апострофа.

## 8) Риски

- Путаница `items.status` и `occurrence_status` останется, если soonest начнёт показывать будущее, а бейдж — прошлое. Оба смотрят на один якорь.
- Пустой `ADMINISTRATOR_EMAIL` оставляет справочник только для чтения. Это безопасный дефолт для прода, где сейчас каждый пользователь `admin`. Роль появится после регистрации этого email и рестарта (или следующего login).
- Старый access с `role=admin` после выкладки kinds писать уже не сможет: проверка ждёт `administrator`.
- Локальный volume со старым seed сам не очистится.
- Integration в CI флапает, если миграции гоняются на грязном томе. Тестовый compose уже на tmpfs; в CI — свой service, БД с нуля.
